Savings Bucket
Technical Implementation Plan — v1.0
Purpose: Bridge the approved Discovery, PRD, SDD, UX/User Journey and Product Backlog into an executable engineering plan.
Architecture baseline: AWS, Python/FastAPI, PostgreSQL, API Gateway, ECS Fargate, EventBridge and SQS.
1. Purpose and Scope
•	Implement the MVP without changing the PRD intent.
•	Buckets are logical allocations, not separate bank accounts.
•	Actual money movement remains authoritative in the banking transaction capability.
•	Use explicit states, idempotency, transactional outbox and reconciliation.
•	Keep AI advisory-only and outside the money-movement path.

3. Target Architecture
Customer → React + TypeScript + Vite web application → API Gateway → OIDC/JWT → ECS/FastAPI services → PostgreSQL. Recurring contributions use EventBridge and SQS/DLQ. Notifications consume domain events. Banking/Core Banking is authoritative for actual account debits/credits.
•	API Gateway: API boundary, routing, throttling and authorization integration.
•	ECS Fargate: FastAPI runtime; EKS is intentionally not used in the current design.
•	RDS PostgreSQL: durable relational store.
•	EventBridge: event routing and scheduling.
•	SQS + DLQ: durable asynchronous processing and failure isolation.
•	Secrets Manager + KMS: secrets and encryption.
•	CloudWatch + tracing: logs, metrics, traces and alerts.
•	VPC/private subnets/security groups: network isolation.
•	Future AI Recommendation Service: isolated advisory boundary.
4. Implementation Principles
•	Money first, allocation second; never show financial success before authoritative confirmation.
•	Never trust the client for identity, bucket ownership or final transaction state.
•	Every money-changing command must be idempotent.
•	Propagate correlation IDs through synchronous and asynchronous flows.
•	Use optimistic concurrency/versioning for competing bucket updates.
•	Use transactional outbox for reliable event publication.
•	Treat PENDING, SUCCESS, FAILED and REVERSED as distinct states.
•	Use reconciliation for uncertain external outcomes.

8. Database Implementation
Table	Key design
buckets	customer_id, target_amount, current_balance, target_date, status, version, timestamps.
bucket_transactions	type, amount, status, external reference, idempotency_key, timestamps.
recurring_contributions	frequency, next_execution_at, status, version.
outbox_events	event_id, aggregate_id, event_type, payload, status, created_at, published_at.
•	Use NUMERIC/DECIMAL for money; never floating point.
•	Use UTC timestamps.
•	Use constraints and foreign keys for important invariants.
•	Index customer, bucket, transaction-history and due-schedule lookups.
•	Use migrations for controlled schema changes.
9. Contribution Workflow
Authenticate and validate bucket ownership.
Require an idempotency key.
Create/retrieve command in PENDING state.
Call authoritative banking capability.
Persist external reference and outcome.
On SUCCESS, update logical allocation transactionally.
Write outbox event and publish asynchronously.
On FAILED, do not increase bucket balance.
On uncertain timeout, keep recoverable and reconcile; never assume failure.
10. Withdrawal Workflow
•	Authenticate and validate ownership.
•	Check available logical allocation.
•	Create idempotent PENDING command.
•	Request authoritative banking transaction.
•	Persist SUCCESS/FAILED/REVERSED and reference.
•	Decrease logical allocation only after confirmed success.
•	Emit outbox event.
•	Use reconciliation for uncertain outcomes.
11. Idempotency, Concurrency and Consistency
Concern	Implementation
Duplicate API request	Idempotency key + persisted command/result.
Duplicate event	Event ID + consumer deduplication.
Concurrent update	Optimistic version check + transaction.
External timeout	PENDING/unknown outcome + reconciliation.
DB commit vs publish	Transactional outbox.
Message failure	SQS retry + DLQ + replay.
Partial workflow	Explicit state machine + recovery/reconciliation.
12. Recurring Contributions
•	Persist schedule and next_execution_at.
•	Trigger due work using EventBridge/EventBridge Scheduler.
•	Send work to SQS for durable processing.
•	Validate schedule status and execution idempotency.
•	Use a unique reference per scheduled occurrence.
•	Reuse the normal contribution workflow.
•	Retry transient failures and route poison messages to DLQ.
•	Notify customer according to outcome.
13. Authentication and Authorization
•	OAuth 2.0 / OpenID Connect with JWT.
•	Validate signature, issuer, audience and expiry.
•	Derive customer identity from the validated token.
•	Check bucket ownership on every operation.
•	Use stronger validation on financial APIs.
•	Store secrets in Secrets Manager.
•	Encrypt data in transit and at rest.
14. Error and Status Model
Status	Meaning
PENDING	Outcome not yet confirmed; customer sees pending.
SUCCESS	Financial movement succeeded and allocation is updated.
FAILED	Financial movement did not complete.
REVERSED	Previously successful movement was reversed.
Use consistent API errors with stable code, safe message, correlation ID and optional field validation. Never expose stack traces or secrets.
15. Observability
•	Correlation IDs on every request/event.
•	Structured logs with sensitive data redacted.
•	Metrics for latency, errors, transaction outcomes, pending age, queue depth, DLQ count and reconciliation exceptions.
•	Distributed tracing where supported.
•	Alerts for sustained failures, DLQ growth, long-pending operations and reconciliation mismatches.

24. Risks and Mitigations
Risk	Mitigation
Duplicate financial command	Mandatory idempotency and unique command keys.
Banking timeout	Explicit PENDING + reconciliation.
Allocation inconsistency	Money first + transaction + outbox + reconciliation.
Duplicate event	Consumer deduplication.
Poison message	Retry + DLQ + replay.
Concurrent updates	Optimistic concurrency.
Sensitive data leakage	Logging redaction + least privilege.
Incorrect AI recommendation	Advisory-only AI with no transaction authority.
