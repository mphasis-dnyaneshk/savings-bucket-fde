1. Document Overview
The MVP covers bucket creation, goal definition, contributions, withdrawals, balance/progress visibility, transaction history, and recurring contributions.
Final architecture decisions: AWS, Python/FastAPI, PostgreSQL, domain-oriented microservices, logical bucket allocation, event-driven recurring contributions, OAuth 2.0/OIDC with JWT, API Gateway + ECS/Fargate, and future AI isolated from financial transaction execution.
2. Architecture Goals
•	Goal-oriented savings without a separate bank account per bucket.
•	Keep actual funds authoritative in the banking account/transaction capability.
•	Safe, auditable contributions and withdrawals with idempotency and explicit states.
•	Independent service scaling without Kubernetes as a runtime dependency.
•	Asynchronous, resilient recurring contributions.
•	Future AI decoupled from money movement.
3. Architecture Principles
•	Domain-oriented service boundaries, not a service per CRUD operation.
•	API Gateway is the north-south API boundary.
•	ECS Fargate is the runtime.
•	RDS PostgreSQL provides ACID transactional state.
•	Use events for asynchronous workflows and controlled commands for money movement.
•	Transactional outbox plus durable messaging.
•	Idempotent consumers and safe retries.
•	AI is advisory only.

7. Application Architecture
 
 
7.1 Service Boundaries
Service	Owns	Responsibilities
Bucket Service	Bucket metadata/logical allocation	Create/read buckets, target validation, balance/progress
Contribution Service	Contribution workflow	Idempotency, banking request, contribution state
Withdrawal Service	Withdrawal workflow	Balance validation, banking request, withdrawal state
Recurring Contribution Service	Recurring config/execution	Scheduling, due commands, retries
Transaction History	Customer-visible history	History read capability; may remain in Bucket Service for MVP
Notification Service	Notification delivery	Consume approved events if enabled
Banking Transaction Service	Actual money movement	Authoritative account debit/credit and result
The boundaries are domain-oriented and intentionally avoid a microservice for every CRUD operation.

8.2 Accounting Model – Decision
A bucket is a logical allocation, not a separate underlying bank account. Actual customer funds remain authoritative in the banking account/transaction capability. The bucket database records allocation across goals. Contribution updates allocation only after confirmed financial success; withdrawal follows the inverse pattern.
8.3 Consistency and Concurrency
•	PostgreSQL transactions for local state changes.
•	Optimistic locking via version or row-level locking for balance updates.
•	Unique customer/idempotency constraints.
•	PENDING, SUCCESS, FAILED and REVERSED states where applicable.
•	Transactional outbox for atomic local state plus event intent.
•	Idempotent event consumers.
•	Reconciliation for financial success without bucket-state completion.

10. Sequence Flows
10.1 Create Bucket
1.	Authenticate customer.
2.	Client calls POST /v1/buckets.
3.	API Gateway validates JWT.
4.	Bucket Service validates and commits bucket to PostgreSQL.
5.	API returns bucket ID, target, balance and progress.
10.2 Add Money
6.	Client sends contribution with Idempotency-Key.
7.	JWT is validated.
8.	Contribution Service validates ownership and amount.
9.	Idempotency is checked.
10.	Banking Transaction Service processes movement.
11.	Result is SUCCESS, FAILED or PENDING.
12.	Confirmed success commits bucket allocation and transaction state.
13.	ContributionCompleted event is published through outbox.
14.	Client receives status and transaction reference.
10.3 Withdrawal
15.	Validate identity and ownership.
16.	Check allocated bucket balance.
17.	Create idempotent withdrawal command.
18.	Request financial movement.
19.	Reduce allocation only after confirmed success.
20.	Record transaction and publish completion event.
10.4 Recurring Contribution
21.	Store recurring configuration and next execution date.
22.	EventBridge Scheduler triggers due execution.
23.	Recurring Service places durable work on SQS.
24.	Contribution Service processes using manual-contribution controls.
25.	Outcome updates execution state and optionally notifies customer.
26.	Next execution is scheduled according to policy.
11. Failure Handling
Failure	Handling
Duplicate request	Return original result; never process a second financial transaction.
Insufficient funds	Reject contribution; allocation unchanged.
Withdrawal exceeds balance	Reject; allocation unchanged.
Banking dependency unavailable	Controlled PENDING/503; never falsely update balance.
Duplicate event	Ignore already-processed event ID.
DB failure before commit	Rollback local transaction.
DB failure after external success	Reconciliation repairs eventual consistency.
Recurring failure	SQS retry, DLQ and alerting.
Unauthorized access	403 without sensitive details.

12. Security Architecture
•	OAuth 2.0/OIDC + JWT authentication.
•	API Gateway validates JWT signature, issuer, audience and expiry.
•	Every service authorizes resource ownership.
•	ECS task roles use least privilege.
•	ECS/RDS use private subnets and restrictive security groups.
•	TLS and KMS-backed encryption at rest.
•	Secrets Manager for credentials.
•	No credentials/tokens/unnecessary sensitive data in logs.
•	Audit financial actions and security failures.

16. Disaster Recovery & Resilience
•	RDS Multi-AZ in production.
•	Automated backups; cross-region backup/replication can support DR.
•	Stateless ECS services can be recreated in a recovery environment.
•	Infrastructure as code enables repeatable recovery.
•	Queues, explicit states and reconciliation protect workflow consistency.
•	DR tests validate financial-state consistency as well as availability.
17. Future AI Architecture
Approved Financial Signals (income / spending / savings / goals / target dates) → AI/Recommendation Layer → Savings Bucket Experience.
•	AI is read-oriented and advisory.
•	AI cannot directly execute financial transactions.
•	Recommendations are guidance, not guaranteed outcomes.
•	Only authorized customer data may be used.
•	AI failure cannot block MVP money movement.
•	Model governance, evaluation, privacy and explainability are required before production.

22. Risks & Mitigations
Risk	Mitigation
Distributed transaction inconsistency	Explicit states, idempotency, outbox and reconciliation
Duplicate event processing	Event IDs, unique constraints and idempotent consumers
Incorrect bucket balance	Single bucket owner, ACID local updates and outcome gating
Service proliferation	Domain boundaries; combine simple reads where justified
AI privacy/model risk	Read-only architecture, governance and controlled rollout
Operational complexity	Managed AWS services and ECS Fargate instead of Kubernetes

24. Final Architecture Summary
The final architecture uses AWS-managed infrastructure with FastAPI microservices on ECS Fargate, PostgreSQL on RDS, API Gateway, OAuth 2.0/OIDC with JWT, and EventBridge/SQS for asynchronous recurring-contribution processing.
Savings Buckets are logical allocations against an authoritative customer account. Financial movement is separated from bucket-domain state, with idempotency, explicit transaction states, transactional outbox and reconciliation providing distributed consistency.
Future AI remains advisory and isolated from core money movement. This provides a concrete, explainable and implementation-ready architecture for the FDE capstone.

•	Bucket accounting is a logical allocation model.
•	Banking account/transaction capability is authoritative for actual money movement.
•	Banking integration is represented by an adapter/interface in the capstone.
•	NFR values are initial design targets and require validation.
